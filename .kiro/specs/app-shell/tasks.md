# Implementation Plan

> app-shell はプロジェクト全体の骨格(Tauri v2 + Vite + React + TypeScript、Rust クレート構成、コンポジションルート、ウィンドウ振り分け、品質ツール、CI)を所有する。下流 spec(capture-library / screen-capture / annotation-editor)はタスク 1 の成果物を前提にする。app-shell 自身に他 spec への依存は無い。
> タスク 1.2・1.5・1.6 は特定の受け入れ基準に対応しない基盤タスクのため、`_Requirements:_` 行を持たない。

- [x] 1. プロジェクト基盤: アプリ骨格・品質ツール・CI
- [x] 1.1 Tauri v2 + Vite + React + TypeScript(strict)のプロジェクトを pnpm で作成する
  - pnpm をパッケージマネージャとして、Vite + React + TypeScript のフロントエンドと `src-tauri/` の Tauri v2 アプリを File Structure Plan のディレクトリ構成どおりに作成する
  - TypeScript は `strict: true`、`@/` を `src/` に解決するパスエイリアスを TypeScript と Vite の両方に設定する
  - Tauri 設定で identifier を `app.snipt`、起動時に作るウィンドウを 0 枚とし、トレイ用を含むアプリアイコン一式を用意する
  - 開発用・ビルド用・テスト用の pnpm スクリプト(dev / build / tauri)を定義する
  - 完了状態: `pnpm install` 後に `pnpm build` でフロントエンドが型エラーなくビルドでき、`pnpm tauri dev` で起動してもウィンドウが 1 枚も表示されない
  - _Requirements: 1.1_

- [x] 1.2 Rust クレートを機能モジュール構成で用意し、各モジュールのスタブを置く
  - クレートの最小 Rust バージョンを 1.90 に定め、`main.rs` はライブラリ側の起動関数を呼ぶだけにする
  - `shared`、`platform::windows`、`app_shell`、`capture_library`、`screen_capture`、`annotation_editor` の各モジュールを空の骨格として作成する
  - 各機能モジュールに共通シグネチャの `setup`(アプリを受け取り成功を返すだけ)を置き、`app_shell` には第 2 段用の `start` スタブも置く
  - `app_shell` は下流モジュールを参照しないという依存方向をモジュール構成で守る
  - 完了状態: `cargo build` と `cargo test` が成功し、全モジュールの `setup` スタブが公開 API として参照できる

- [x] 1.3 コンポジションルートにプラグイン登録順と 2 段階 setup を実装する
  - 公式プラグイン(single-instance を最初に、続けて global-shortcut / autostart / notification / dialog / log)とトレイ機能を有効化した Tauri 依存を追加して登録する。single-instance のコールバックはこの時点ではログ出力のみとする
  - ログの出力先を `%LOCALAPPDATA%\app.snipt\logs` に設定する
  - setup の中で `app_shell::setup` → `capture_library::setup` → `annotation_editor::setup` → `screen_capture::setup` → `app_shell::start` の順に呼び、いずれかの失敗はログを残してアプリ起動失敗として扱う
  - プラグイン登録と command 登録(`generate_handler!`)を spec ごとのコメント区画に分け、下流 spec が自分の区画へ追記するだけで済む形にする(capture-library の opener プラグイン用区画を含む)
  - 完了状態: `pnpm tauri dev` で起動するとログに 5 段の setup がこの順で記録され、2 つ目のプロセスを起動しても常駐プロセスが 1 つのままになる
  - _Requirements: 1.1, 6.1_

- [x] 1.4 フロントエンドの入口とウィンドウラベルによるビュー振り分けを作る
  - 入口で React を起動し、現在のウィンドウラベルに応じて `settings` / `history` / `editor-<captureId>` / `overlay-<monitorIndex>` を各機能のルートコンポーネントへ振り分ける
  - 各機能(app-shell / capture-library / annotation-editor / screen-capture)の公開入口に、規約どおりの名前付き export としてプレースホルダの `SettingsWindow` / `HistoryWindow` / `EditorWindow({ captureId })` / `OverlayWindow({ monitorIndex })` を置き、遅延読み込みする
  - 振り分け表を spec ごとの区画に分け、下流 spec はプレースホルダを置き換えるだけで済むようにする
  - 未知のラベルでは何も描画せずログに残す
  - 完了状態: 各ラベル名から期待するプレースホルダが選ばれることが確認でき、`editor-abc` から `captureId = "abc"`、`overlay-1` から `monitorIndex = 1`(数値)が渡る
  - _Requirements: 1.4, 3.1_

- [x] 1.5 lint・format・テストのツールを導入する
  - Rust: rustfmt の設定と、clippy を警告エラー扱い(`-D warnings`)で実行する設定を用意し、`cargo test` が走る最小の単体テストを 1 つ置く
  - TypeScript: ESLint(`any` 禁止を含む TypeScript 向けルール、React Hooks ルール)と Prettier を導入し、互いの整形ルールが衝突しないようにする
  - Vitest を `@/` エイリアス付きで導入し、React コンポーネントを描画して検証できるテスト環境(DOM 環境と Testing Library)と Tauri API のモック方法を整え、1.4 の振り分けロジックの単体テストを置く
  - Rust の結合テスト用に Tauri のモックランタイム(test 機能)を開発依存として有効にする
  - lint / format チェック / test をまとめて実行できる pnpm スクリプトを定義する
  - 完了状態: `cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test`、`pnpm lint`、`pnpm format:check`、`pnpm test` がすべて成功する

- [x] 1.6 GitHub Actions の CI を windows-latest で構成する
  - push / pull request で windows-latest 上に Rust(stable、MSVC、clippy・rustfmt 付き)、Node.js 20+、pnpm を用意し、依存をキャッシュする
  - 1.5 の全チェック(rustfmt、clippy、cargo test、ESLint、Prettier、Vitest)と、フロントエンドビルドおよび Tauri アプリのビルド(インストーラのバンドルなし)を実行する
  - 完了状態: ワークフロー定義がリポジトリにあり、いずれかのチェックまたはビルドが失敗したときにジョブが失敗する構成になっている

- [x] 2. 共有契約とアクセラレータ
- [x] 2.1 下流と共有する Rust の型とトレイトを定義する
  - キャプチャ種別、キャプチャ要求の受け口トレイト(非ブロッキング、busy 時の無視は実装側の責任)、通知の重要度・通知内容・通知トレイトを定義する
  - 設定(3 つのホットキー、全画面の対象、保存先フォルダ、自動起動)とホットキー設定・全画面対象・正規化済みアクセラレータ文字列を、design のシリアライズ表記(camelCase)で定義する
  - ピクチャフォルダを受け取って既定値(PrintScreen / Ctrl+PrintScreen / Shift+PrintScreen、カーソルのあるモニタ、`<ピクチャ>\Snipt`、自動起動有効)を作る生成関数を用意する
  - 完了状態: 単体テストで既定値の 3 キー・保存先・自動起動有効が確認でき、設定を JSON にすると design の永続形式と同じキー名・値表記になる
  - _Requirements: 1.3, 2.1, 2.2, 3.2, 4.4, 5.3_

- [x] 2.2 (P) WebView 側の IPC 契約を Rust と一対一で定義する
  - キャプチャ種別、全画面対象、ブランド付きアクセラレータ、設定、ホットキー状態、失敗種別、設定更新エラー(6 種)の型を定義する
  - `settings_get` / `settings_update` / `settings_check_save_dir` / `hotkeys_status` / `hotkeys_retry` / `hotkeys_suspend` / `hotkeys_resume` の型付きラッパーと、設定変更イベント名を提供する
  - 完了状態: 型チェックが通り、Vitest でラッパーが正しい command 名と引数で呼び出すこと(invoke をモック)が確認できる
  - _Boundary: src/shared/ipc_
  - _Requirements: 3.2, 3.3, 3.4, 3.5, 3.7, 3.8_

- [x] 2.3 (P) Windows の PrintScreen 予約設定を読む platform アダプタを作る
  - `windows` クレート依存を追加し、現在のユーザーのキーボード設定から「PrintScreen キーで画面キャプチャを開く」の値を読み、有効 / 無効 / 値なしを返す
  - 読み取り失敗は値なしとして扱い、パニックしない
  - 完了状態: Windows 上の単体テストで呼び出しが値(有効 / 無効 / なし)のいずれかを返して終了する
  - _Boundary: platform keyboard_settings_
  - _Requirements: 2.4_

- [x] 2.4 アクセラレータの正規化・検証・変換・表示を実装する
  - 入力文字列を修飾子順(Ctrl, Alt, Shift, Win)と W3C のキー名に正規化し、非修飾キーが無い・修飾なしで許されないキー(文字キー単独など)・未知のキーを区別して拒否する。修飾なしは PrintScreen、F1〜F24、Pause、ScrollLock のみ許す
  - 正規化済みアクセラレータを global-shortcut のショートカットへ変換し、利用者向けの表示文字列(例「Ctrl + PrintScreen」)を作る
  - 完了状態: 単体テストで PrintScreen と Ctrl+PrintScreen の往復、修飾子順の正規化、文字キー単独の拒否が確認できる
  - _Depends: 2.1_
  - _Requirements: 2.1, 3.3_

- [x] 3. 設定の検証・永続化・保持
- [x] 3.1 設定の検証と保存先の書き込み可否チェックを実装する
  - 3 つのホットキーの重複を検出し、重複したキーと関係する操作を返す。各ホットキーのアクセラレータ検証結果を操作ごとに返す
  - 保存先を絶対パスに正規化し、フォルダが無ければ作成したうえで一意名の一時ファイルを作成・削除できるかで書き込み可否を判定する
  - 完了状態: 単体テストで重複が検出され、読み取り専用フォルダが「書き込み不可」として拒否される
  - _Requirements: 3.4, 3.7_

- [x] 3.2 設定ファイルの読み込みと原子的な保存を実装する
  - スキーマバージョン付きの形式で一時ファイルへ書いてから置き換える保存を行う
  - 読み込みでは欠落項目を既定値で補い、JSON 不正・型不一致・未知のバージョン・不正または重複したアクセラレータを破損とみなして、退避ファイルへ移したうえで既定値を保存し直し「破損から復旧」を返す
  - ファイルが無い初回は既定値を保存し、既定の保存先フォルダの作成を試みる(失敗はログのみ)
  - 完了状態: 単体テストで初回の既定値と `Pictures\Snipt`、不正 JSON と重複キーからの復旧(退避ファイルが残る)、保存 → 読み込みの往復一致が確認できる
  - _Requirements: 2.1, 4.1, 4.2, 4.3, 4.4, 5.3_

- [x] 3.3 確定済み設定の唯一の保持者 SettingsStore を実装する
  - 現在の設定のスナップショット取得、変更購読(コールバック登録、登録順・ロック外で同期呼び出し)を提供する
  - 確定は永続化が成功したときだけ設定を置き換えて購読者を呼び、失敗時は以前の設定のまま失敗を返す
  - 完了状態: 単体テストで確定成功時に購読者が 1 回だけ新しい設定で呼ばれ、永続化失敗時は購読者が呼ばれず値も変わらない
  - _Requirements: 3.8, 4.1, 4.2_

- [x] 4. グローバルホットキー
- [x] 4.1 ショートカット登録の抽象と global-shortcut による実装を用意する
  - 登録・解除・全解除の 3 操作を持つバックエンド抽象を定め、global-shortcut プラグイン経由の本番実装と、テスト用に失敗を注入できるフェイク実装を用意する
  - 完了状態: フェイクで任意のキーの登録失敗を再現でき、本番実装がクレート内でビルドできる
  - _Requirements: 2.2, 2.3_

- [x] 4.2 HotkeyManager の初回登録・適用とロールバック・失敗分類を実装する
  - 初回登録で 3 操作それぞれの登録結果(登録済みか、失敗種別)を状態として保持する
  - 設定変更の適用では変更された操作の旧キーを先にすべて解除してから新キーを登録し、1 つでも失敗したら新キーを解除して旧キーを再登録し、操作ごとの状態を失敗として返す(キーの入れ替えにも対応する)
  - 修飾なしの PrintScreen が失敗し、Windows の予約設定が「無効」と確認できない場合は「Windows による予約」、それ以外は「競合」に分類する
  - 失敗中の操作だけを再登録する再試行と、現在の状態一覧の取得を提供する
  - 完了状態: フェイクを使った単体テストで、2 件目の失敗時に旧キーへ完全に戻ること、範囲 ⇔ ウィンドウのキー交換が成功すること、予約設定の値(1 / 値なし / 0)と修飾の有無に応じた分類が確認できる
  - _Depends: 2.3, 2.4_
  - _Requirements: 2.1, 2.3, 2.4, 3.5_

- [x] 4.3 ホットキーの一時停止・再開・全解放とキー押下の解決を実装する
  - 一時停止で全キーを解除し、再開で現在の設定を再登録する(二重の一時停止・再開でも状態が崩れない)
  - 終了用に全キーを解放する操作を提供する
  - 押されたショートカットから対応するキャプチャ種別を引く対応表を、適用・再試行のたびに更新する
  - 完了状態: フェイクを使った単体テストで、一時停止中は何も登録されておらず、再開後に 3 キーが登録され、全解放後は登録が 0 件になり、各ショートカットが正しい種別に解決される
  - _Requirements: 2.2, 3.3, 7.1_

- [x] 5. 通知・自動起動・キャプチャ転送・終了前フック
- [x] 5.1 (P) OS トースト通知の Notifier 実装を作る

  - 完了状態: Notifier トレイトとして管理状態に登録できる実装があり、表示失敗を模した場合も呼び出しが正常に戻る

- [x] 5.2 (P) OS 自動起動の同期を実装する

  - 完了状態: フェイクを使った単体テストで、無効化の希望で disable が呼ばれ、OS 側が無効のときに有効化の希望で enable が呼ばれ、状態が一致していれば何も呼ばれない

- [x] 5.4 (P) 終了前フックの登録口と結果集約を実装する

  - 再試行のたびに再実行できる(フックが冪等である前提を契約として明示する)

- [x] 6. 設定確定サービスと command
- [x] 6.1 設定確定をオールオアナッシングで行う SettingsService を実装する
  - 検証 → 保存先チェック → ホットキー適用 → 自動起動同期 → 永続化 → 保持値の置き換えと購読者呼び出し → 全ウィンドウへの設定変更イベント送信、の順で処理する

- [x] 7. ウィンドウ・終了・トレイ
- [x] 7.1 settings / history ウィンドウを開く・前面化する WindowManager を実装する
  - 同じラベルのウィンドウがあれば最小化解除・表示・フォーカスし、無ければアプリの画面で生成する(settings は 560×640 固定・中央、history は 960×640 可変)
  - 閉じたウィンドウは破棄する
  - 完了状態: Tauri のモックランタイムを使ったテストで、設定を 2 回開いても settings ラベルのウィンドウが 1 枚のままで、履歴を開くと history ラベルのウィンドウが生成される
  - _Requirements: 1.4, 3.1_

- [x] 7.2 (P) 終了処理と多重起動時の通知を Lifecycle に実装する
  - 終了は二重実行を防いだうえで終了用ワーカースレッドで行い、終了前フックの結果に未保存が残れば件数と内訳を示す確認(再試行 / 破棄して終了 / キャンセル)を表示する。再試行はフックを再実行し、キャンセルは何も変えずに常駐を続ける
  - 終了確定時は全ホットキーを解放し、全ウィンドウを破棄してからアプリを終了する
  - 2 つ目のプロセス起動を検知したら既存側で「Snipt は既に起動しています。…」を通知する
  - ウィンドウを閉じたことによる終了要求(終了コードなし)は抑止し、明示的な終了だけを許す判定を提供する
  - 完了状態: 確認表示を差し替え可能にした単体テストで、未保存 0 件なら即終了手順へ進み、再試行で未保存が消えれば終了し、キャンセルではホットキー解放もウィンドウ破棄も起きない
  - _Boundary: Lifecycle_
  - _Depends: 4.3, 5.1, 5.4_
  - _Requirements: 6.1, 7.1, 7.2, 7.3, 7.4, 7.5_

- [x] 7.3 トレイアイコン・メニュー・ツールチップを TrayController に実装する

## Implementation Notes
- 1.2/1.3: 各 spec の `setup` と `app_shell::start` は `pub fn setup<R: tauri::Runtime>(app: &mut tauri::App<R>) -> Result<(), Box<dyn std::error::Error>>` とランタイムについて汎用にした。本番は `Wry` で design のシグネチャと同じ呼び方になり、テストではモックランタイムで `snipt_lib::setup_specs` を実行できる(`src-tauri/tests/setup.rs`)。
- 1.3: `platform::windows` は `#[cfg(windows)]` で囲み、Linux でもクレートがビルド・テストできるようにした。
- 1.5: TypeScript は typescript-eslint の対応範囲に合わせて 6.0 系に固定した(7.0 は未対応)。
- 1.5(PR #4 のレビューで変更): ESLint + Prettier の代わりに oxlint + oxfmt を使う。Vite 8 の oxc 系ツールに揃えるため。ツールのバージョンは mise(`mise.toml`)で固定し、CI も `mise run check:web` / `check:rust` で実行する。
- 2.1: `Accelerator` は `pub(crate) fn from_normalized` でのみ生成する。serde の読み込みは検証を通らないため、設定ファイル読み込み(3.2)で `accelerator::parse` による再検証を行う。
- 2.4: キー名は W3C の `KeyboardEvent.code` と大文字小文字まで一致させる(`printscreen` は不可)。修飾子名は大文字小文字を問わず、`Control` / `Meta` / `Super` などの別名も受け付けて正規化する。
- 3.1: ホットキーの検証は正規化した値で重複を比べ、不正なキーを先に、次に最初の重複を返す。読み取り専用フォルダの単体テストは Unix の権限ビットで行い(root では権限が無視されるため、その場合は書き込めることを確認する)、Windows では「親がファイルで作成できないフォルダ」を書き込み不可として確認する。Windows の ACL による書き込み禁止は手動 E2E で確認する。
- 3.2: `schemaVersion` が無いファイルも「未知のバージョン」として破損扱いにする。`hotkeys` はキー単位で既定値と合わせるため、1 つだけ欠けたファイルでも残り 2 つは維持される。読み込み時にアクセラレータを正規化した値に置き換える。退避ファイル名が同じ秒で重なったときは `-1` などの連番を付ける。
- 3.3: `SettingsStore::load` / `commit` は 6.1(SettingsService)と 9.1(第 1 段 setup)で使うまで `expect(dead_code)` を付けている。使い始めたら外す(外し忘れはコンパイルエラーになる)。下流からは `crate::shared::SettingsStore` でも参照できる。
- 4.1: フェイク(`hotkeys::backend::fake::FakeBackend`)は OS と同じく、登録済みのキーの二重登録を失敗にする。キー交換が「旧キーを先に全部解除」していないと失敗するので、4.2 の順序をテストで確かめられる。今は `#[cfg(test)]` なので、10.1 の結合テスト(`tests/`)で使うときは公開方法を決める。
- 4.2: 予約設定の読み取りは `ReservationProbe` として注入する(本番は `HotkeyManager::windows_probe()`)。ロールバック時の戻り値は、変更しようとした操作について新しいキーと失敗種別(成功したが巻き戻したものは失敗なし・未登録)、変更していない操作は現在の状態を返す。
- 4.3: global-shortcut プラグインはキー押下ハンドラをメインスレッドで呼び、登録処理はメインスレッドでの実行を待つ。デッドロックを避けるため、ショートカット → 種別の対応表は状態とは別のロックに置き、`mode_for` はそちらだけを読む。一時停止中の `apply` は設定値の記録だけ行い、`resume` で登録する。
- 5.1: `ToastNotifier` は表示処理を差し替えられる形にして、表示失敗のテストを OS に依存せず行う。通知の内容はレベルに応じたログにも残す。
- 5.2: `AutostartSync::new` はデバッグビルドで OS 側を変更しない。テストは OS 変更ありの内部コンストラクタでフェイクを使う。
- 5.4: `BeforeExitHooks` / `ExitCheck` は `crate::shared` からも参照できる。`run_all` はロックを外してから登録順にフックを呼ぶので、フックの中から `register` しても固まらない。`run_all` は 7.x(終了処理)で使うまで `expect(dead_code)` を付けている。
- 5.x(CI で判明): Windows ではライブラリの単体テストの実行ファイルにも Common Controls v6 のマニフェストが必要になった(無いと STATUS_ENTRYPOINT_NOT_FOUND)。`build.rs` は tauri-build のマニフェスト埋め込みを止め、`windows-app-manifest.xml` を全リンク対象(アプリ本体・単体テスト・結合テスト)へ `/MANIFEST:EMBED` で埋め込む。
- 6.1: 自動起動の同期は値が変わったときだけ行う(変わっていないのにレジストリ読み取りの失敗で他の設定が保存できなくなるのを避ける)。`settings://changed` の送信は差し替え可能な関数として受け取り、9.x の配線で `app.emit` を渡す。ツールチップ更新は 9.2 で SettingsStore の購読として行う。
- 6.2: app の command をウィンドウ単位で許可するため、`build.rs` の `AppManifest::commands` に全 command を列挙する(下流 spec は自分の区画に追記する)。生成される `src-tauri/permissions/autogenerated/` は .gitignore に入れた。capability の対象と権限は単体テストで確認する。
- 7.2: 確認表示(`ExitConfirm`)と終了手順(`ExitActions`)をトレイトにして、単体テストではフェイクに差し替える。本番は dialog プラグインのメッセージボックス(再試行 / 破棄して終了 / キャンセル)と、ホットキー全解放 → メインスレッドで全ウィンドウ破棄(完了を待つ) → `app.exit(0)`。`quit` はワーカースレッドで `quit_blocking` を呼ぶ。キャンセル後は再び終了できる。
- 7.3: メニュー構成とクリックの対応は純粋な関数(`action_for_menu` / `action_for_icon` / `tooltip_text`)にしてテストし、転送先は `TrayTargets` トレイトで受け取る。トレイの生成(`create`)と `refresh_tooltip` の呼び出しは 9.2 で配線する。未登録時のツールチップは「Snipt - 範囲キャプチャ: 未登録」とした。
- 8.1: 修飾キーなしで使えないキー(文字キーなど)を単独で押したときは確定せず、「Ctrl / Alt / Shift / Win のいずれかと組み合わせてください」と欄に表示する。Tab と Esc の単独押しはブラウザに任せる(フォーカス移動のため)。
- 8.2: 編集すると以降は `settings://changed` で下書きを置き換えない。保存エラーは次の編集で消え、重複は下書きから常に計算する。`hotkeyRegistrationFailed` は該当欄と全体の両方に表示する。
- 8.4: `@tauri-apps/plugin-dialog` は Rust 側(2.8.3)に合わせて `~2.8.3` にした。
- 8.5: バナーは表示時に状態を取得する。保存のたびに `key` を変えて再取得する。
- 8.6: 閉じるボタンのため capability に `core:window:allow-close` を追加した。最低限のスタイル(`settings.css`、ダークモード対応)を付けた。
